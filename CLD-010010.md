# CLD-0110: Blocked Sign-In Attempts Investigation

## Original Ticket

<img width="1913" height="933" alt="image" src="https://github.com/user-attachments/assets/aea073ed-b35c-485d-9ef7-a1a8bbe546ee" />


**Short Description:**

Blocked sign-in attempts from known attacker infrastructure.

**Description:**

Rule **"Watchlist IP activity"** fired.

Three sign-in attempts for **daniel.reeve@cloudora.io** occurred between **05:09 and 05:11 UTC** from **102.89.44.17 (Lagos, Nigeria)**.

All three attempts returned **error 53003** and were blocked by a **Conditional Access policy**.

The source IP already existed on the tenant block list and had previously been identified as attacker infrastructure during **CLD-0001 (August executive account takeover).**

Evidence: `evidence/cloudora_signins.csv`.

---

## Investigation Strategy

Before beginning the investigation, I considered two possible explanations.

**Malicious hypothesis:**

An attacker attempted to authenticate using compromised credentials but was prevented from gaining access by Conditional Access policies.

**Benign hypothesis:**

A legitimate user was traveling or using a VPN, causing a false alert.

---

## Evidence Reviewed

I reviewed the sign-in activity associated with **daniel.reeve@cloudora.io**.

The authentication timeline showed three consecutive sign-in attempts originating from **102.89.44.17**.

All three attempts failed with **error 53003**, indicating that Conditional Access blocked the requests.

<img width="1354" height="101" alt="image" src="https://github.com/user-attachments/assets/3d99ad26-244f-401a-84c6-351d2048d312" />


I then compared the source IP against previously documented incidents.

The address already existed on the tenant block list and had been identified during **CLD-0001**, which immediately increased confidence that the activity was malicious.

---

## Investigation Process

My first objective was determining whether the account had been compromised.

The most important observation was that **every authentication attempt was blocked before access was granted**.

No successful authentications were identified.

Because the IP address had already been documented as attacker infrastructure, I ruled out the possibility of legitimate travel or normal user activity.

The evidence confirmed that the attacker attempted to access the account, but the organization's security controls prevented the intrusion.

At that point, the investigation shifted from determining whether an attack occurred to determining whether any additional response actions were necessary.

Because the authentication attempts never succeeded, no evidence suggested post-authentication activity.

No additional investigation was required.

---

## Verdict

**True Positive (Blocked)**

An unauthorized authentication attempt occurred, but Conditional Access controls successfully prevented account access.

---

## Severity

### Sev 4 – Low-impact security event that was successfully contained by existing security controls.

**Why this severity was assigned:**

The authentication attempts were malicious and generated a legitimate alert.

However, the security controls functioned as designed and prevented account access.

Because the attack was successfully blocked, the incident was assigned a lower severity.

---

## Response Actions

- Documented the blocked authentication attempts.
- Verified that the source IP remained on the tenant block list.
- Confirmed that Conditional Access policies successfully prevented authentication.
- Closed the investigation.

---

## Justification

The alert represented a legitimate attack attempt.

However, all authentication attempts failed before access was granted.

The existing security controls successfully contained the threat and prevented account compromise.
